06 · Agent Loop Deep Dive

The agent loop is a turn state machine

This page goes one layer deeper than the overview. It explains how Pi moves between model streaming, tool execution, queued user messages, turn hooks, and final shutdown.

Read with source open. Keep packages/agent/src/agent-loop.ts and packages/agent/src/types.ts beside this page. The names below match the implementation.

The two loops

The important shape is not one loop, but two. The inner loop handles assistant turns and tool calls. The outer loop gives queued follow-up messages one last chance after the agent would otherwise stop.

while true:                         // outer: follow-up drain
  hasMoreToolCalls = true

  while hasMoreToolCalls or pendingMessages:
    inject pending steering/follow-up messages
    assistant = streamAssistantResponse(...)
    toolResults = execute tool calls, if any
    prepareNextTurn?()
    shouldStopAfterTurn?()
    pendingMessages = getSteeringMessages?()

  followUpMessages = getFollowUpMessages?()
  if followUpMessages:
    pendingMessages = followUpMessages
    continue

  break

One assistant turn, expanded

input
Context enters as AgentMessage[]. This is Pi's app-level message type. It can include normal LLM messages and app-specific messages added through declaration merging.
transform
transformContext can rewrite the message list. Use this for context-window work before provider conversion.
convert
convertToLlm creates provider-readable messages. This is the boundary where custom app messages must become normal Message[] or be filtered out.
stream
streamSimple returns model events. The loop stores a partial assistant message on start, updates it on text/thinking/tool-call deltas, and replaces it with the final message on done or error.
tools
Tool calls become tool-result messages. The loop validates arguments, runs tools, applies hooks, emits tool events, and appends toolResult messages to context.
next
The next turn starts only if something requires it. More tool calls, steering messages, or follow-up messages keep the run alive. Otherwise agent_end finishes the run.

Streaming boundary

streamAssistantResponse is where Pi stops being app-specific and calls the model provider. It builds a Context with systemPrompt, converted messages, and tools.

Sequential and parallel tool batches

When an assistant message contains multiple tool calls, Pi chooses one of two execution paths. Sequential mode fully prepares, runs, finalizes, and emits each call before moving to the next. Parallel mode still prepares calls in assistant order, but executes allowed tools concurrently and then emits tool-result messages in the assistant's original call order.

executeToolCalls(...)
  toolCalls = assistantMessage.content.filter(type === "toolCall")
  hasSequentialToolCall = any tool has executionMode === "sequential"

  if config.toolExecution === "sequential" or hasSequentialToolCall:
    executeToolCallsSequential(...)
  else:
    executeToolCallsParallel(...)

Early termination is conservative

A tool result may set terminate: true, but the batch stops future tool turns only when every finalized tool result in the batch asks to terminate. This avoids one tool accidentally hiding other tool results the model asked for in the same assistant message.

function shouldTerminateToolBatch(finalizedCalls):
  return finalizedCalls.length > 0
    and every finalized.result.terminate === true
